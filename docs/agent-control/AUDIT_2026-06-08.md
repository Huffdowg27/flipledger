**Goal:** Confidence/hardening pass to determine whether FlipLedger is solid enough to
**replace InventoryLab (30–60 days)** and run **unattended on a VPS**. Bar is higher than
"match IL" — it's "can FlipLedger *be* the system of record."

**Method:** Read-only audit across 4 domains — Calc correctness, Data completeness,
Reliability (unattended ops), Portability. Findings ranked P0–P3. **No code changed.**

Severity: **P0** wrong numbers / data loss · **P1** trust risk / blocks IL-replacement ·
**P2** hardening / latent bug · **P3** nice-to-have.

## Findings

### F1 [P1] — Profit math is centralized in name only; 8 routes inline divergent formulas
`CLAUDE.md` mandates all profit/ROI/margin go through `calculations.ts`. Reality:
**only 1 file imports it.** 8 route handlers inline their own profit math:

| Surface | Inline formula |
|---|---|
| `merchant-sales/route.ts:89` | `salePrice - buyCost - fees + shippingProfit` |
| `ebay-sales/route.ts:71` | `salePrice - buyCost - fees + shippingProfit` |
| `fba-sales/route.ts:75` | `salePrice - buyCost - fees` (no shipping term) |
| `wfs-sales/route.ts:67` | `salePrice - buyCost - fees` (no shipping term) |
| `dashboard/route.ts:276` | `revenue - cogs - fees` (no shipping, no clawback) |
| `dashboard/route.ts:493` | projected: `revenue - cogs - estimatedFees` |
| `in-flight-orders/route.ts:73` | `revenue - cogs - estimatedFees - mfnShipping` |
| `profitability/route.ts:200` | ROI inline: `(profit / cogs) * 100` |

The canonical `calculateProfit()` carries a `feeClawbacks` term that **every** inline version
drops. **Risk:** once IL is retired, FlipLedger is the sole source of truth — any divergence
between dashboard / per-channel sales pages / profitability becomes an *undetectable* wrong
number. This is the single largest drift surface for the IL-replacement goal.
**Current numeric impact: unverified** (formulas may be equivalent for given inputs — needs
per-surface trace in the fix phase). **Fix:** route every surface through `calculations.ts`;
add a test asserting each surface equals the canonical result for sample rows.

### F2 [P1] — $3,646.55 of revenue is booked at $0 COGS (profit overstated), and it's ongoing
75 line items / 76 units across 32 ASINs on **non-canceled, shipped** orders have
`cogs_per_unit = 0/NULL` because the SKU/ASIN has **no `inventory_ledger` lot** → FIFO finds no
batch → COGS silently stays $0. Profit on those sales is overstated by their true cost.
**Not stale** — recurring: 9 items in 2026-06, 10 in 2026-05, trickling back to 2025-01.
**Fix:** (a) backfill missing buy lots for the 32 ASINs; (b) — more important — see F4: there is
no guardrail, so this re-accumulates invisibly.

### F3 [P2] — FIFO ASIN-fallback can double-consume lots on multi-SKU ASINs (latent)
`getSalesByAsin` (fifo.ts:132) assigns a sale to a SKU's lots when the sale's own SKU has no
lot but its ASIN does. In `recalcAll`, if **one ASIN has ≥2 SKUs that each carry lots**, every
one of those SKU passes pulls the *same* orphan-SKU sale and consumes it from *its own* lots —
depleting multiple SKUs' inventory for a single sale, with `cogs_per_unit` overwritten by
whichever SKU is processed last. **Surface is large:** 1,549 ASINs have lots under >1 SKU.
**Currently not firing via null SKUs** (0 null/empty-SKU sales), but *can* fire for non-empty
SKUs that lack their own lot. **Fix:** in `recalcAll`, claim each orphan-ASIN sale by exactly one
SKU (e.g., the lot-bearing SKU with oldest stock) instead of letting every SKU pass re-consume
it. Verify live prevalence first.

### F4 [P2] — No guardrail surfaces silent $0-COGS / unmatched sales (systemic)
F2 is invisible until someone runs an ad-hoc query. For FlipLedger to *replace* IL, silent
profit overstatement is the exact failure mode that erodes trust. **Fix:** a standing "data
integrity" panel/report (and/or a post-sync log line) that counts: shipped units with $0 COGS,
sales whose SKU/ASIN has no lot, and any negative-remaining lots — so these can never hide.

**F3 (FIFO determinism) — diagnosed precisely, fix verified on a DB copy:**
- The real symptom was **non-idempotency**, not double-$: original `recalcAll` rewrites the
  **same 5 items on every run** (cost-neutral, total stable at $514,409.04, but unstable per-SKU).
- Cause: orphan-SKU sales on multi-SKU ASINs are claimed by whichever SKU runs last (alphabetical).
- Fix: process SKUs oldest-lot-first + claim each ASIN-fallback sale exactly once (deterministic,
  true cross-SKU FIFO). Verified on a copy: total unchanged, recalc becomes idempotent.

### ⚠️ Two important catches from this session

- **F5 (DEBUNKED): no $4,663 COGS drift.** An early test ran `recalcAll` via bare `tsx` WITHOUT
  `FIFO_IL_INFINITE=true`, which turned `il:` import lots finite and zeroed overflow units —
  a **test-harness artifact**, not a data bug. With the flag on (as in pm2) the live DB is
  converged and correct. Lesson: never run a FIFO recalc without the env flag.

- **F6 (NEW, P1 for VPS): FIFO correctness silently depends on `FIFO_IL_INFINITE=true`.**
  `ecosystem.config.js` sets it, but a VPS started via bare `npm start` / a different process
  manager / a one-off recalc script would omit it and **silently destroy ~$4,663+ of COGS** (it
  fails OPEN). For the VPS-migration goal this is the most dangerous landmine found. Recommended
  fix: make infinite-lot the safe default (opt-OUT flag), or hard-fail/loud-warn when `il:` lots
  exist and the flag is unset. Not auto-applied (semantics change — needs sign-off).

**Not mutated on live (by design):** no `recalcAll` run, no COGS backfill run, no deploy — these
move real COGS/profit and were left for explicit approval. The committed changes are code-only and
inert until deployed.
